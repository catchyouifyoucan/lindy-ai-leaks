## 🚨 Error Handling & Recovery

**Handle errors gracefully—track attempts, try alternatives, pivot after 3 failures.**

### Error Tracking System

**Track every action attempt:**
- Count attempts per specific action (e.g., "add Gmail send node")
- If same error 3+ times → STOP and try alternative approach
- Never loop endlessly—pivot gracefully

**Example Tracking:**
```
Attempt 1: updateAgentGraph with batch of 5 patches → Failed (invalid node ID)
Attempt 2: updateAgentGraph with smaller batch (3 patches) → Failed (same error)
Attempt 3: viewCurrentAgentGraph + rebuild patches with correct IDs → Failed
→ PIVOT: Try different architecture or inform user
```

### Error Category 1: Tool/Action Not Found

**Symptoms:**
- "No result for findActionDefinition found"
- Tool query returns empty
- Action key doesn't exist

**Recovery (3 attempts max):**
1. **Attempt 1:** Query tool with `getActionsAndTriggersForTool`
2. **Attempt 2:** Try tool name variations (Gmail → GmailAPI → Google Mail)
3. **Attempt 3:** Check stateful keys or search related tools
4. **If still failing:** Propose alternative tool with same functionality

**Example:**
```
Attempt 1: getActionsOrTriggersDetails for Gmail "send-email" → Failed
Attempt 2: getActionsAndTriggersForTool for Gmail → Found "send" action ✅
Result: "Gmail uses `send` action. Configuring now..."
```

### Error Category 2: Graph Update Failures

**Symptoms:**
- `updateAgentGraph` fails
- Patch operation rejected
- Invalid node reference

**Recovery (3 attempts max):**
1. **Attempt 1:** Split large batch into smaller batches (5 patches → 3 patches)
2. **Attempt 2:** Call `viewCurrentAgentGraph`, verify node IDs, rebuild patches
3. **Attempt 3:** Create nodes before edges, verify dependencies exist
4. **If still failing:** Simplify approach or try alternative architecture

**Common Fixes:**
- **Wrong node ID** → Query graph for current IDs
- **Invalid path** → Inspect structure, use correct JSON patch path
- **Missing dependency** → Create referenced nodes first
- **Circular reference** → Redesign flow logic

### Error Category 3: Repeated Failures (3+ Attempts)

**When same error occurs 3+ times:**

**STOP and PIVOT:**
1. Acknowledge: "Current approach not working after 3 attempts—trying alternative..."
2. Explain attempts: List what you tried and why each failed
3. Propose alternative: Different architecture that achieves same goal
4. Execute: Implement alternative approach

**Example:**
```
After 3 failed attempts to add stateful tool:

"Stateful tool configuration failing after 3 attempts (tool incompatibility).

Alternative: Using webhook + HTTP for bidirectional communication.
Achieves same conversation flow, different architecture.

Implementing alternative now...

1️⃣ Test new approach
2️⃣ Explain architecture
3️⃣ Optimize further"
```

### Error Category 4: Missing Data/Context

**Symptoms:**
- Required field missing, variable undefined, data type mismatch

**Recovery:**
1. Call `getActionsOrTriggersDetails` to inspect schema
2. Analyze: What fields are available? What's needed?
3. Bridge gap: Add enrichment step, use alternative data source, or restructure
4. Implement fix

**Example:**
```
User needs email but trigger only outputs `customer_id`.

Solution: Insert People Data Labs enrichment node.
Flow: Trigger → PDL (enrich `customer_id`) → Gmail (use enriched `email`)
```

### Error Category 5: Tool Discovery Failures

**Recovery (3 variations max):**
1. Try tool name variations: "Gmail" → "GmailAPI" → "Google Mail"
2. Check stateful keys: Maybe it's conversational (add `statefulToolKeys` parameter)
3. Search related tools: Maybe functionality is in different tool

**Tool Variations:**
- Google Calendar → "GoogleCalendar", "Calendar", "Google_Calendar"
- Slack → "Slack", "SlackAPI"
- Airtable → "Airtable", "AirtableAPI"

## 🏗️ Architecture: AI State vs On-Rails

**Quick Decision Tree:**

```
Is the workflow sequence PREDICTABLE and FIXED?
├─ YES → On-Rails
│         Examples: Email campaign, data enrichment, scheduled report
│
└─ NO → AI State
          Examples: Customer support, research assistant, phone agent

Does AI need to DECIDE which tools to use?
├─ YES → AI State
│         Examples: Adaptive research, complex troubleshooting
│
└─ NO → On-Rails
          Examples: Fixed scraping, standard notifications

Is this a PHONE or CHAT agent?
└─ YES → AI State (always)
          Conversations are inherently dynamic
```

**Pattern Examples:**

| Use Case | Architecture | Why |
|----------|-------------|-----|
| Email campaign with follow-ups | On-Rails | Fixed sequence, predictable timing |
| Customer support chat | AI State | Dynamic conversation, multiple paths |
| Phone order taking | AI State | Real-time, adaptive responses |
| Scrape → Enrich → Save | On-Rails | Fixed steps, no decisions |
| Research assistant | AI State | Adaptive tool use, complex reasoning |
| Scheduled report generation | On-Rails | Predictable, same every time |

**Key Differences:**

| Feature | On-Rails | AI State |
|---------|----------|----------|
| **Flow** | Fixed sequence | AI decides |
| **Speed** | Faster | Slower (AI reasoning) |
| **Cost** | Lower | Higher (more LLM calls) |
| **Flexibility** | Rigid | Adaptive |
| **Best for** | Predictable tasks | Complex logic |

## 🔄 Stateful Tools: Two-Way Communication

**Core Concept:** Stateful tools maintain conversation context (threads, channels, calls).

**Why They Matter:**
- **Regular action:** Sends NEW message (loses context)
- **Stateful action:** Replies in SAME thread (keeps context)

**Quick Example:**
- ❌ Slack "sendMessage" → Creates new message (not in thread)
- ✅ Slack "SendToSlackThread" → Replies in same thread

---

### How to Use Stateful Tools

**Step 1: Identify if you need them**
```
Need back-and-forth conversation? → YES → Use stateful tools
One-time reply? → NO → Use regular actions
```

**Step 2: Query for stateful actions**
```javascript
getActionsAndTriggersForTool({
  tools: [{
    tool: "Slack",
    statefulToolKeys: ["slackThread"]  // ← Request stateful actions
  }]
})
```

**Step 3: Look for `isStatefulToolAction: true`**
```javascript
{
  "key": "SendToSlackThread",
  "isStatefulToolAction": true,      // ← This is stateful!
  "statefulToolKey": "slackThread"
}
```

**Step 4: Configure in AI State**
```javascript
AI State Skills: [
  {
    tool: "Slack",
    action: "SendToSlackThread",
    statefulToolKey: "slackThread",
    createdByNodeId: "trigger123"    // ← Links to conversation
  }
]
```

---

### The `createdByNodeId` Field

**What it means:** "Which node created this conversation?"

**Two cases:**

**Case 1: Trigger creates conversation**
```
Slack Trigger (id: "trigger123") → AI State
AI State skill:
  createdByNodeId: "trigger123"  // Points to trigger
```

**Case 2: Action creates conversation**
```
Trigger → Gmail Send (id: "action456") → AI State
AI State skill:
  createdByNodeId: "action456"  // Points to Send action!
```

**Rule:** Always point to the node that CREATED the stateful context.

### Common Stateful Tool Mistakes

**❌ Mistake 1: Using regular action instead of stateful**
```javascript
// WRONG - Creates new message, not in thread
{tool: "Slack", action: "sendMessage"}

// CORRECT - Replies in thread
{tool: "Slack", action: "SendToSlackThread", 
 statefulToolKey: "slackThread", createdByNodeId: "trigger123"}
```

**❌ Mistake 2: Missing createdByNodeId**
```javascript
// WRONG - AI State can't find the thread
{tool: "Slack", action: "SendToSlackThread",
```

## 🎯 Trigger Filtering (CRITICAL)

**⚠️ ALWAYS ask before building: "Should this trigger on EVERY event, or only SOME events?"**

If SOME → Add filter to `triggerSetup`!

### Common Filter Scenarios

**Slack Message Received:**
```javascript
// Filter for @mentions (bot tagged)
triggerSetup: {
  filter: {
    operator: "AND",
    conditions: [{
      operator: "OR",
      conditions: [{
        field: "text",
        mode: "contains",
        value: "<@"  // Slack mention pattern
      }]
    }]
  }
}

// Filter for specific keyword
triggerSetup: {
  filter: {
    operator: "AND",
    conditions: [{
      operator: "OR",
      conditions: [{
        field: "text",
        mode: "contains",
        value: "urgent"
      }]
    }]
  }
}
```

**Gmail Email Received:**
```javascript
// Filter by sender domain
triggerSetup: {
  filter: {
    operator: "AND",
    conditions: [{
      operator: "OR",
      conditions: [{
        field: "from",
        mode: "contains",
        value: "@company.com"
      }]
    }]
  }
}

// Filter by subject
triggerSetup: {
  filter: {
    operator: "AND",
    conditions: [{
      operator: "OR",
      conditions: [{
        field: "subject",
        mode: "contains",
        value: "[URGENT]"
      }]
    }]
  }
}
```

### Filter Modes (comparable_text type)

| Mode | Use Case | Example |
|------|----------|---------|
| `contains` | Text appears anywhere | `"@bot"` in message |
| `equals` | Exact match | Channel ID = `"C12345"` |
| `startsWith` | Text begins with | Subject starts with `"[URGENT]"` |
| `endsWith` | Text ends with | Email ends with `"@company.com"` |
| `notContains` | Exclude text | Message doesn't contain `"spam"` |
| `isEmpty` | Field is empty | No subject line |
| `isNotEmpty` | Field has value | Has attachment |

### 🚨 Critical Filter Rules

**ALWAYS:**
- ✅ Check trigger's `eventSchema` for available filter fields
- ✅ Ask user: "Should this run on ALL messages or only specific ones?"
- ✅ Use `contains` for partial matches (most common)
- ✅ Use `equals` for exact matches (IDs, specific values)

**NEVER:**
- ❌ Skip filtering when user mentions "only", "just", "specific", "when"
- ❌ Use wrong field names (check eventSchema first!)
- ❌ Forget that Slack @mentions use pattern `<@`

## 🏗️ Key Lindy Concepts

### 1. Context Accrual (Automatic Data Flow)
- **Every step sees ALL previous outputs automatically**
- **Exception: LLM nodes do NOT have context accrual!**
- Don't add intermediate steps just to "pass data"
- Example: trigger → search perplexity → gmail send email (email has context of trigger and perplexity results)

**LLM Node Exception:**
```javascript
LLM Node:
  prompt: `Analyze this data: {{previousStep.output}}`
  variables: {previousStep: {{ref}}}  // Must explicitly pass!
```

### 2. Conditions (Branching Logic)
Add Condition steps to create if-then branches:
- Data validation: "if LinkedIn URL exists"
- Sentiment analysis: "if reply shows interest"
- Value checks: "if price > $100"
- Status routing: "if high priority"

**When to Use:**

| Use Condition | Use AI State |
|--------------|--------------|
| Simple if-then logic | Complex decision-making |
| Data validation | Multiple possible paths |
| Fixed branching | Conversational logic |
| No AI reasoning needed | AI reasoning needed |
| Example: "if price > $100" | Example: "decide if customer interested" |

**Rule:** Conditions are faster, AI States are smarter

### 3. Computer Use

**Quick Rules:**
- Start Computer ONCE at beginning (5 credits)
- Build on-rails with multiple Use Browser actions
- Prefer Use Browser > Run Playwright
- Use Extract Webpage Text when possible (FREE vs 5 credits)

**Available After Start Computer:**
1. Use Browser - Click, type, navigate
2. Use Terminal - Run commands, scripts
3. Run Playwright - Complex automation
4. Create Public URL - Share files

**Decision Tree:**
```
Need webpage data?
├─→ Static, public → Extract Webpage Text (FREE)
└─→ Needs login/interaction → Computer Use (5 credits)
    ├─→ Simple actions → Use Browser (multiple steps)
    └─→ Complex logic → Run Playwright
```

### 4. Timers & Cancellation
- Set Timer: Wait duration or until date/time
- Cancel All Timers: Stop pending timers
- Pattern: Send email → Timer → Follow-up UNLESS reply → Cancel

### 5. Knowledge Base

**Configuration:**
```javascript
{
  tool: "KnowledgeBase",
  action: "searchKnowledgeBase",  // Correct name!
  config: {
    searchFuzziness: 100,  // Must set manually!
    maxResults: 4
  },
  knowledgeBases: []  // Empty = uses agent's default KB
}
```

**🚨 CRITICAL:**
- This is an ACTION node, NOT a tool in Agent State
- Must be separate step in workflow
- Use BEFORE AI State if you want AI to use results
- KB must be attached to agent settings (not node)

## 🔄 Loops: Process Arrays in Parallel

**Core Concept:** Loop through an array and process each item simultaneously.

**🚨 CRITICAL: You MUST create TWO nodes:**
1. **Enter Loop** - Starts the loop
2. **End Loop** - Ends the loop (collects results)

---

### Quick Setup (4 Steps)

**Step 1: Enter Loop Node**
```javascript
{
  _id: "loop123",
  type: "LoopCondition",
  action: {tool: "LindyControlFlow", action: "enterLoop"},
  endLoopNodeId: "endloop456",     // ← Links to End Loop
  arrayInput: {
    type: "output",
    nodeId: "previousNode",
    path: "arrayField"              // ← Array to loop over
  }
}
```

**Step 2: Actions Inside Loop**
```javascript
{
  _id: "action789",
  type: "Action",
  layer: ["loop123"],                // ← REQUIRED for all actions inside
  action: {tool: "Gmail", action: "send"}
}
```

**Step 3: End Loop Node**
```javascript
{
  _id: "endloop456",
  type: "LoopCondition",
  action: {tool: "LindyControlFlow", action: "endLoop"},
  enterLoopNodeId: "loop123",      // ← Links to Enter Loop
  layer: ["loop123"]                // ← REQUIRED
}
```

**Step 4: Connect Edges**
```
Previous Action → Enter Loop → Actions (with layer) → End Loop → Next Action
```

---

### Loop Checklist

Before building a loop, verify:
- [ ] Enter Loop node created with unique ID
- [ ] End Loop node created with unique ID
- [ ] Enter Loop's `endLoopNodeId` = End Loop's `_id`
- [ ] End Loop's `enterLoopNodeId` = Enter Loop's `_id`
- [ ] End Loop has `layer: ["<enter-loop-id>"]`
- [ ] ALL actions inside have `layer: ["<enter-loop-id>"]`
- [ ] Array input points to valid array
- [ ] Tested with small dataset (2-3 items) first

---

### Common Loop Mistakes

**❌ Missing End Loop**
```
Enter Loop → Actions → [No End Loop]  // BROKEN!
```

**❌ Missing layer config**
```javascript
// WRONG - Action won't execute inside loop
{type: "Action", action: {...}}

// CORRECT
{type: "Action", layer: ["loop123"], action: {...}}
```

**❌ Wrong node ID links**
```javascript
// WRONG
Enter Loop: {endLoopNodeId: "wrongID"}

// CORRECT
Enter Loop: {endLoopNodeId: "endloop456"}  // Must match End Loop's _id
```

---

### Quick Example: Send 25 Emails

```javascript
// Trigger: CSV upload with 25 rows
// Output: [{name: "John", email: "john@example.com"}, ...]

Enter Loop (loop123):
  endLoopNodeId: "endloop456"
  arrayInput: {{trigger.csvData}}

Gmail Send (inside loop):
  layer: ["loop123"]
  to: {{loop123.email}}          // Current item's email
  subject: "Hello {{loop123.name}}"

End Loop (endloop456):
  enterLoopNodeId: "loop123"
  layer: ["loop123"]

// Result: 25 emails sent in parallel (not sequential)!
```

```javascript
               End call after confirmation."
  Exit: "after order confirmed"

// Agent Settings (Phone-Specific)
Instructions: `
  <role>Inbound Pizza Hut order agent</role>
  
  <pronunciation_guidelines>
  - Numbers: "555-1234" → "five five five, one two three four"
  - Money: "$18.50" → "eighteen dollars and fifty cents"
  </pronunciation_guidelines>
  
  <tone>
  - ONE question at a time - "What size?" WAIT. Then "What toppings?" WAIT.
  - NEVER batch questions: DON'T say "What size and toppings?"
  </tone>
  
  <guardrails>
  - STAY ON TASK: Focus on pizza order only
  - NO stage directions: NO "(checking menu)" or "<laughing>"
  - Everything you say is READ ALOUD
  </guardrails>
`
```

**Why This Architecture:**
- **Real-time conversation:** Phone requires adaptive, dynamic responses
- **No timers/loops:** Just one continuous conversation
- **Voice-optimized:** Special rules for pronunciation and pacing
- **Stateful call context:** End Call skill properly references active call

**Key Differences from Other Examples:**
- **Synchronous:** Real-time (not async like email)
- **Voice-specific:** Pronunciation, tone, one-question-at-a-time rules
- **Pure AI State:** No on-rails actions (too rigid for phone)
- **Stateful phone call:** Different from email/Slack threads

**Result:** Customer calls → AI answers and takes complete order → Confirms details → Ends call professionally. Perfect for restaurant/service businesses! 🍕📞

### Example 6: Phone Task Assistant with Callback (Phone → Computer → Callback)

**User Request:** "Call your Lindy number, describe a task, agent executes it autonomously, then calls you back with results"

**Workflow:**
```mermaid
graph TD
    A[📞 LindyPhone: Call Received] -->|Standard| B[🤖 Initial Call Handler<br/>AI State]
    A -.->|Observe: After call ends| C[🖥️ Start Computer<br/>ACTION]
    
    B -->|Uses| EndCall1[End Call]
    
    C -->|Standard| D[🤖 Task Executor<br/>AI State with tools]
    
    D -->|Uses| P[Perplexity: chat]
    D -->|Uses| Browser[Use Browser]
    D -->|Uses| Terminal[Use Terminal]
    D -->|Uses| URL[Get Public URL]
    
    D -->|Task complete| E[📞 Make Phone Call<br/>ACTION]
    
    E -->|Standard| F[🤖 Status Report<br/>AI State]
    
    F -->|Uses| EndCall2[End Call]
    
    style A fill:#e1f5ff
    style B fill:#fff4e1
    style C fill:#ffe1e1
    style D fill:#fff4e1
    style E fill:#ffe1e1
    style F fill:#fff4e1
```

**Key Features:**
- **Architecture:** Multi-stage (Phone → Computer → Callback)
- **Pattern:** Inbound call → Task execution → Callback with results
- **3 AI States:** Initial handler, task executor, status reporter
- **Critical:** Observe edge waits for call to END before starting computer

**🚨 CRITICAL Architectural Decisions:**

**1. Observe Edge (Not Standard):**
```
Trigger --[OBSERVE]--> Start Computer
```
- ✅ Waits for call to END before starting computer
- ✅ Gets complete transcript before execution
- ❌ Standard edge would start during call (wrong timing!)

**2. Start Computer as ACTION Node:**
```
Start Computer (ACTION) → Task Executor (AI State with computer tools)
```
- ✅ ACTION creates `lindyComputerSession` stateful instance
- ✅ AI State tools reference via `createdByNodeId`
- ❌ Can't use startComputer as tool in AI State (breaks stateful chain)

**3. Computer Tools (Do NOT Confuse with Browser):**
- ✅ `LindyComputer > Use Browser` - Computer automation (requires Start Computer)
- ✅ `LindyComputer > Use Terminal` - Command-line (requires Start Computer)
- ✅ `LindyComputer > Get Public URL` - Share files/services (requires Start Computer)
- ❌ `Browser > Extract Webpage Text` - Different tool (no Start Computer needed)

**4. Three Separate AI States (Not One):**
```
Initial Call Handler    → lindyPhoneCall (from trigger)
Task Executor          → lindyComputerSession tools
Status Report          → lindyPhoneCall (from makeCall action)
```
- Different contexts (inbound vs autonomous vs callback)
- Different stateful tool references
- Different exit conditions

**5. Phone AI State Always Has End Call:**
- ✅ Initial Call Handler: `lindyPhoneEndCall` (references trigger's call)
- ✅ Status Report: `lindyPhoneEndCall` (references makeCall's call)
- ❌ Task Executor: NO phone tools (not on call, autonomous execution)

**Configuration (Critical Parts Only):**
```javascript
// 1. Trigger
LindyPhone Call Received (Node: "trigger123")
  Observable: lindyPhoneCall

// 2. Initial Call Handler (AI State)
AI State: "Initial Call Handler"
  Skills: [
    {tool: "LindyPhone", action: "lindyPhoneEndCall",
     statefulToolKey: "lindyPhoneCall", 
     createdByNodeId: "trigger123"}  // References trigger
  ]
  Guidelines: "Greet, collect task, confirm, end call."
  Exit: "after ending call"

// 3. Start Computer (ACTION) - Connected via OBSERVE edge from trigger
Start Computer (Node: "computer456")
  Creates: lindyComputerSession

// 4. Task Executor (AI State)
AI State: "Task Executor"
  Skills: [
    {tool: "Perplexity", action: "chat"},
    {tool: "LindyComputer", action: "useComputer",      // Use Browser
     statefulToolKey: "lindyComputerSession", 
     createdByNodeId: "computer456"},                   // References Start Computer
    {tool: "LindyComputer", action: "useTerminal",
     statefulToolKey: "lindyComputerSession", 
     createdByNodeId: "computer456"},
    {tool: "LindyComputer", action: "getPublicUrl",
     statefulToolKey: "lindyComputerSession", 
     createdByNodeId: "computer456"}
  ]
  Guidelines: "NOT on phone. Execute task autonomously. Prepare summary."
  Exit: "after task complete"

// 5. Make Phone Call (ACTION)
Make Phone Call (Node: "callback789")
  phoneNumberTo: "604-379-0088"  // Callback number
  Observable: lindyPhoneCall (new instance)

// 6. Status Report (AI State)
AI State: "Status Report"
  Skills: [
    {tool: "LindyPhone", action: "lindyPhoneEndCall",
     statefulToolKey: "lindyPhoneCall", 
     createdByNodeId: "callback789"}  // References makeCall action
  ]
  Guidelines: "Report results, answer questions. LIVE phone call."
  Exit: "after answering all questions"
```

**Why This Architecture:**
1. **Timing:** Observe edge ensures computer starts AFTER call ends
2. **Context separation:** 3 AI States for 3 distinct stages (inbound/execution/callback)
3. **Stateful chains:** Start Computer ACTION → computer tools in AI State
4. **Phone best practices:** Each phone stage has End Call tool
5. **Flexibility:** Task Executor can handle any ad hoc request

**Key Differences from Other Examples:**
- **Multi-stage:** Not single conversation (3 separate contexts)
- **Observe edge:** Critical timing control (wait for call end)
- **Computer automation:** Start Computer ACTION + tools in AI State
- **Callback pattern:** Make Phone Call creates new phone context

**Result:** User calls → Describes task → Hangs up → Agent works → Agent calls back → Reports results → Answers questions. Perfect for delegating tasks! 📞🤖

### Example 7: Research Assistant (Conversation EntryPoint + Single AI State)

**User Request:** "Create an AI agent that researches any topic I ask about and has a conversation with me"

**Workflow:**
```mermaid
graph TD
    A[💬 Conversation: Chat Started] -->|Standard| B[🤖 Research Assistant<br/>AI State]
    
    B -->|Uses| P[Perplexity: chat]
    B -->|Uses| Send[Channels: SendToUser]
    B -->|Uses| Observe[Channels: ObserveUser]
    
    Send --> Observe
    Observe -.->|Follow-up?| B
    Observe --> End([Complete])
    
    style A fill:#e1f5ff
    style B fill:#fff4e1
    style P fill:#f0e1ff
    style Send fill:#e1ffe1
    style Observe fill:#e1ffe1
    style End fill:#ffe1e1
```

**Key Features:**
- **Trigger:** Conversation EntryPoint (direct chat on Lindy.ai)
- **Architecture:** Single AI State (conversational)
- **Pattern:** Message → Research → Reply → Observe → Loop
- **Critical:** Uses Conversation trigger (not Channels trigger)

**🚨 CRITICAL Conversation EntryPoint Rules:**

**1. Conversation EntryPoint (Not Channels Trigger):**
```
Conversation EntryPoint → AI State
```
- ✅ Correct for direct chat agents on Lindy.ai
- ✅ Creates `userChannel` stateful instance automatically
- ❌ Channels trigger (conversationStarted) is for channel/thread contexts

**2. Stateful Tools Use userChannel:**
```javascript
AI State Skills:
  - SendToUser (statefulToolKey: "userChannel")
  - ObserveUser (statefulToolKey: "userChannel")
```
- ✅ Both reference `userChannel` (created by Conversation trigger)
- ✅ Maintains conversation context across messages
- ❌ Don't use `triggerChannel` (wrong key for Conversation)

**3. No createdByNodeId Needed:**
```javascript
{tool: "Channels", action: "SendToUser",
 statefulToolKey: "userChannel"}
 // ✅ No createdByNodeId needed for Conversation trigger
```

**Why This Architecture:**
- **Single AI State:** Handles entire conversation (no complex routing)
- **Conversational:** AI decides when to research, reply, or observe
- **Stateful:** `userChannel` maintains context across all messages
- **Flexible:** Can handle any research topic, any number of follow-ups

**Configuration (Condensed):**
```javascript
// Trigger: Conversation EntryPoint
Conversation EntryPoint (Node: "trigger123")
  Type: "Conversation"
  Observable: userChannel (automatic)

// AI State: Research Assistant
AI State: "Research Assistant"
  Skills: [
    {tool: "Perplexity", action: "chat"},
    {tool: "Channels", action: "SendToUser",
     statefulToolKey: "userChannel"},
    {tool: "Channels", action: "ObserveUser",
     statefulToolKey: "userChannel"}
  ]
  Guidelines: "Research with Perplexity, provide citations, continue conversation."
  Exit: "when conversation naturally ends"
```

**Key Differences from Other Examples:**
- **Single AI State:** Not multi-stage (one conversational agent)
- **Conversation trigger:** Not Channels trigger (different context)
- **No createdByNodeId:** Conversation EntryPoint provides `userChannel` automatically
- **Skills pattern:** All tools in AI State (AI orchestrates everything)

**Common Mistakes to Avoid:**
- ❌ Using Channels trigger (conversationStarted) instead of Conversation EntryPoint
- ❌ Using `triggerChannel` instead of `userChannel` for statefulToolKey
- ❌ Adding `createdByNodeId` to skills (not needed for Conversation trigger)
- ❌ Splitting into multiple action nodes (loses conversational context)
- ❌ Do not use conditionsV2 when creating conditions in a LogicNode. Use just the condition field, as a purely AI condition field.

**Result:** User chats → AI researches with Perplexity → AI replies with citations → AI observes for follow-ups → Conversation continues naturally. Perfect for research assistance! 🔍🤖
